**LANDING_DESIGN_CONTEXT.md — дизайн и макет лендинга производства полиуретановых изделий**  
***Назначение:*** *контекст и дизайн-бриф для Codex при работе с публичным сайтом на Next.js. Это* ***не утверждённый заказчиком финальный дизайн*** *и не требование немедленно реализовать все анимации.*  
***Правило приоритета:*** *прямые новые указания пользователя → согласованные требования проекта / актуальный код → этот дизайн-бриф. Не делать вид, что художественные предложения в этом файле согласованы заказчиком.*  
  
---  
**1. Что создаём и зачем**  
Проект — **одностраничный корпоративный сайт-каталог** для производства полиуретановых изделий. Компания преимущественно изготавливает детали **под заказ, в том числе по чертежам клиентов**. Сайт нужен для презентации производственных направлений и получения обращений, а не для продажи товара без менеджера.  
**Основной пользовательский сценарий:**  
1. Посетитель за несколько секунд понимает, что производит компания.  
2. Видит категории деталей, реальные фотографии / примеры продукции и краткие описания.  
3. Понимает, что можно заказать изготовление по своему чертежу.  
4. Легко находит телефон, мессенджер или форму заявки и отправляет запрос.  
Целевая аудитория по ответу заказчика: промышленные предприятия, организации и частные лица. Тон коммуникации — **компетентный, деловой, простой**, без чрезмерно рекламных обещаний.  
**Не строить:** интернет-магазин, корзину, онлайн-оплату, личный кабинет покупателя, страницу каждого товара или отдельные страницы категорий, сложные фильтры, автоматический расчёт стоимости, конструктор страниц, блог или CRM.

**2. Зафиксированные требования и ещё не утверждённые идеи**  
**Подтверждено по переписке с заказчиком**  
- Нужен **один лендинг**: отдельных страниц категорий не требуется.  
- Основные направления: **втулки, отбойники, демпферы, манжеты**. Дополнительно важно изготовление деталей **по чертежам**.  
- На сайте размещаем сведения о компании, услугах, продукции и контактах.  
- **Цены не показываем**: вместо них обращение для расчёта.  
- Нужна форма заявки, допускающая **одно необязательное вложение**: чертёж, фотографию или ТЗ.  
- Заявки сохраняются на backend и доступны в админке; Telegram-уведомления можно добавить по отдельному решению.  
- Категории, их названия, описания, фотографии, порядок отображения и контакты редактируются через админку.  
- **Заказчик разрешил начать работу над макетом**, но не утвердил готовый визуальный стиль.  
**Актуальное направление макета, согласованное с разработчиком**  
- Небольшой **плавающий скруглённый хедер** с якорной навигацией.  
- Лёгкая, нежная и воздушная эстетика: крупная читаемая типографика, много свободного пространства, мягкие поверхности и аккуратная сетка.  
- **Каталог как основной визуальный акцент**: четыре крупные editorial-секции; изображение детали и текст чередуются слева/справа.  
- Мягкие анимации появления и переходов при прокрутке, возможная смена цвета фона между категориями.  
- Первоначальная экспериментальная идея — **вращение 3D-моделей при скролле**. Это **опция для отдельной оценки**, не базовое требование, и 3D-моделей пока нет.  
- Палитра макета: почти белый фон, мягкие голубые поверхности, синие акценты и тёмный сине-серый текст. Точные оттенки можно уточнять по макету.  
При разработке первого макета сначала показать **убедительный статический дизайн**; дополнительные анимации обсуждать отдельно. Визуальная выразительность не должна зависеть от WebGL.

**4. Информационная архитектура: один маршрут** `/`  
**Меню с якорями, а не переходами на товарные страницы.** Предлагаемый порядок секций:  
  
|  |  |  |  |  
| - | - | - | - |  
| **№** |  **Якорь** |  **Секция** |  **Смысл / CTA** |  
| 01 |  `#top` |  Header + первый экран |  Чем занимается компания, «Смотреть продукцию», «Отправить заявку» |  
| 02 |  `#catalog` |  Продукция |  Четыре категории с фото и описаниями, CTA для запроса |  
| 03 |  `#custom` |  Изготовление по чертежам |  Клиент может заказать нестандартную деталь, «Рассчитать изготовление» |  
| 04 |  `#about` |  О производстве / о компании |  Реальные факты и производственные возможности |  
| 05 |  `#services` |  Услуги |  Фактически оказываемые услуги, не выдумывать список |  
| 06 |  `#request` |  Форма заявки |  Имя, телефон, описание задачи, один файл |  
| 07 |  `#contacts` |  Контакты |  Телефон, e-mail при наличии, адрес, мессенджеры, опционально карта |  
| 08 |  — |  Footer |  Повтор контактов, юридические ссылки / политика обработки данных |  
  
   
**Примечания:**  
- Порядок секций — дизайн-предложение, допускает перестановку после обсуждения.  
- «О компании» и «Услуги» можно компактно объединить, если мало материалов; **не создавать пустые блоки ради длины страницы**.  
- Каталог не обязан выглядеть как обычная сетка маленьких товарных карточек. По исходной идее предпочтительнее **четыре визуально крупных блока**.  
- Для якорей использовать `scroll-margin-top`, учитывая фиксированный/плавающий хедер.  
- Не выдумывать отдельные товары, точные размеры, цены, преимущества или характеристики материала.

**5. Композиция desktop-макета (ориентир 1440 px)**  
**5.1. Header**  
**Цель:** минимум шума, быстрый путь к нужному разделу.  
- Плавающая горизонтальная капсула/скруглённый прямоугольник, расположенный не вплотную к верхней границе.  
- Слева — название/логотип (до предоставления — нейтральный текстовый placeholder), по центру — 3–5 якорей, справа — контактный CTA.  
- Не перегружать меню ссылками. Пример: «Продукция», «Услуги», «О компании», «Контакты», «Оставить заявку».  
- Лёгкая полупрозрачная поверхность или матовая подложка допустима, **но не превращать интерфейс в glassmorphism**.  
- При прокрутке хедер не должен перекрывать контент или прыгать по высоте.  
- Нужны `:focus-visible`, полноценная клавиатурная навигация, достаточные размеры клика.  
**5.2. Первый экран / Hero**  
**Композиция:** крупный заголовок, короткое пояснение и два ясных действия; отдельное изображение в первом экране не используется.  
Пример иерархии (текст **временный**, не утверждён):  
- Надзаголовок: «ПРОИЗВОДСТВО ПОЛИУРЕТАНОВЫХ ИЗДЕЛИЙ».  
- `h1`: «Детали из полиуретана под ваши задачи» или «Изготовление изделий из полиуретана».  
- Подзаголовок: «Втулки, отбойники, демпферы и манжеты. Производство деталей по чертежам и техническим требованиям».  
- Primary CTA: «Отправить заявку» → `#request`.  
- Secondary CTA: «Смотреть продукцию» → `#catalog`.  
Правила:  
- Главный заголовок должен объяснять **предмет работы компании**, а не быть абстрактным слоганом.  
- Не добавлять непроверенные цифры («20 лет опыта», «1000 заказчиков» и т. п.).  
- Изображение — реальная продукция после получения фото; сейчас допускается **явно помеченный placeholder**.  
- Визуальный объект может располагаться справа от текста или занимать отдельную выразительную композиционную область. Не делать generic hero из случайной стоковой фотографии завода.  
**5.3. Каталог / продуктовая история**  
**Самая важная визуальная часть страницы.** Четыре категории:  
1. Втулки.  
2. Отбойники.  
3. Демпферы.  
4. Манжеты.  
**Desktop-сценарий:** крупные секции в двухколоночной композиции, чередование:  
```  
Каталог / направление 01  
 ┌────────────────────────┬──────────────────────────┐  
 │      ФОТО / ОБЪЕКТ     │  01 / ВТУЛКИ             │  
 │                        │  Название                │  
 │                        │  Описание (2–4 строки)   │  
 │                        │  [Обсудить изготовление] │  
 └────────────────────────┴──────────────────────────┘  
   
 Каталог / направление 02  
 ┌────────────────────────┬──────────────────────────┐  
 │  02 / ОТБОЙНИКИ        │       ФОТО / ОБЪЕКТ      │  
 │  Название              │                          │  
 │  Описание (2–4 строки) │                          │  
 │  [Отправить заявку]    │                          │  
 └────────────────────────┴──────────────────────────┘  
   
 … далее аналогично для «Демпферы» и «Манжеты».  
   
```  
- На desktop: визуальная колонка может занимать около 50–60%, текстовая — 40–50%; конкретная сетка уточняется макетом.  
- Название категории — основной типографический акцент; декоративные номера и индексы не добавлять.  
- 1–3 изображения на категорию, если реально предоставлены. Можно использовать главное изображение и небольшую подборку, но **не выдумывать несуществующие SKU**.  
- CTA может открывать общую форму, при необходимости подставляя `categoryId` для контекста заявки.  
- На странице **нет цен, корзины, артикула, карточек товара и кнопки «Купить»**.  
- Верстать категории **из API**, а не жёстко прошивать четыре элемента: админ сможет добавить, скрыть или переставить категории.  
- `sort_order` из API определяет порядок; `is_published` — публичную видимость.  
- Для 0 опубликованных категорий — аккуратный empty state в разработке и без сломанной секции в production.  
**5.4. Изготовление по чертежам**  
Самостоятельный смысловой акцент после каталога:  
- Короткое, конкретное объяснение индивидуального изготовления.  
- Действие: «Отправить чертёж на расчёт» → общая форма.  
- Небольшая графическая иллюстрация процесса возможна, **но не выдавать графику за реальный чертёж клиента**.  
- Можно компактно показать понятную схему «Опишите задачу → Прикрепите файл → Мы свяжемся с вами», не обещая сроки расчёта без данных.  
**5.5. О компании / производстве**  
- Заголовок о компании, 1–3 абзаца **только по предоставленным данным**.  
- Фотографии цеха/оборудования — **только реальные** или явно помеченные временные изображения на этапе прототипа.  
- Возможны 2–3 фактических преимущества, если заказчик их подтвердит.  
- Никаких вымышленных сертификатов, станков, объёмов выпуска, географии поставок.  
**5.6. Услуги**  
- Простой редакционный список или аккуратная сетка реальных услуг, не очередные 12 одинаковых карточек.  
- Если список услуг не подтверждён, использовать placeholders и пометку «требуется информация от заказчика».  
- Подумать, не дублирует ли секция каталог и «Изготовление по чертежам».  
**5.7. Заявка**  
**Форма должна восприниматься как простой способ связаться, а не как сложный заказ.**  
Предлагаемые поля согласно текущему API:  
- `name` — имя, обязательно.  
- `phone` — телефон, обязательно.  
- `comment` — описание задачи, необязательно.  
- `categoryId` — необязательно, может подставляться из CTA категории без отдельного поля в UI.  
- `file` — **максимум одно вложение**, необязательно.  
Интерфейс:  
- Чёткие подписи, не только placeholder внутри поля.  
- Загрузка файла с понятным состоянием: выбранный файл, размер, удалить/заменить.  
- Формулировка: «Прикрепить чертёж, фото или ТЗ».  
- По текущему API-документу лимит до **10 МиБ**, поддерживаемые форматы: PDF/JPG/JPEG/PNG/WEBP/DOCX/DWG/DXF; перед реализацией сверить с актуальным backend-контрактом.  
- Состояния: пустая форма, валидация, отправка, успех, ошибка, ограничение файла.  
- Не очищать все введённые данные при сетевой ошибке.  
- После успешной отправки — короткое сообщение «Заявка отправлена. Мы свяжемся с вами», без обещания времени ответа.  
- Подтверждение согласия с обработкой данных / ссылка на политику — согласовать юридический текст с владельцем.  
**5.8. Контакты + footer**  
- Из API (`GET /api/v1/contacts`) показывать реальный телефон и другие заполненные поля: email, адрес, часы работы, Telegram, WhatsApp.  
- Телефон кликабелен (`tel:`), email — `mailto:`, ссылки на мессенджеры — только если указаны.  
- **Яндекс Карты — условная опция**, если получен фактический адрес/координаты и принято решение добавлять виджет. Не подставлять случайные координаты.  
- Карта может загружаться лениво ближе к экрану или по действию пользователя; не ухудшать скорость первого экрана.  
- Footer не дублирует бессмысленно всю страницу. Ссылки на политику и необходимые юридические сведения — по согласованию.

**6. Актуальное направление визуальной системы**  
**6.1. Арт-дирекшн**  
Образ: **лёгкость и воздушность + понятная промышленная тематика + спокойная уверенность**.  
- Мягкая округлая кириллическая типографика с крупными читаемыми заголовками; не использовать декоративные точки, счётчики и техническую нумерацию.  
- Качественные предметные изображения с контролируемым светом и фактурой.  
- Чистые границы, почти незаметные разделители, чёткие геометрические линии.  
- Много свободного пространства, но не в ущерб компактности информации.  
- Преимущественно светлые поверхности и мягкий контраст; текст и элементы управления должны оставаться хорошо читаемыми.
- Компактный белый хедер-капсула с мягкой тенью и свободным пространством вокруг, по ощущению похожий на облачко.  
- Плавные переходы белого и голубого в фоне; мягкие многослойные тени и светлые градиенты придают поверхностям объём. В секции изготовления используются медленные шейдерные переливы и абстрактные объекты Motion; при снижении движения остаётся статичная сцена, а при недоступности WebGPU — статичный градиент. Контраст текста сохраняется.
- Не делать вид, будто производитель — luxury-бренд; дизайн должен оставаться промышленным и практичным.  
**6.2. Цвета — только стартовые токены для прототипа**  
  
|  |  |  |  
| - | - | - |  
| **Токен** |  **Предварительное значение** |  **Назначение** |  
| `--color-bg` |  `#F8FBFD` |  Основная светлая поверхность |  
| `--color-text` |  `#213B50` |  Основной сине-серый текст |  
| `--color-surface` |  `#E5F3F9` |  Мягкие голубые поверхности |  
| `--color-muted` |  `#607D8D` |  Второстепенный текст |  
| `--color-accent` |  `#326F91` |  Синий акцент и основные действия |  
| `--color-border` |  `#DCEAF0` |  Мягкие разделители |  
  
   
Точные оттенки можно уточнять при доработке макета. Цвет изделия на фото **не обязан** совпадать с бренд-акцентом.  
**6.3. Типографика**  
- Использовать мягкую округлую sans-serif гарнитуру с кириллицей (в текущем макете — Nunito Sans); второй шрифт — только при явной дизайн-причине.  
- Примерный масштаб: `h1` 56–84 px на широком desktop, заголовки секций 38–64 px, основной текст 16–19 px. Это **ориентиры, не фиксированные значения**.  
- Не использовать десятки одновременно жирных и акцентных элементов. Hierarchy важнее украшений.  
- Читаемая длина строк текста, хорошие интервалы, насыщенность по смыслу.  
**6.4. Сетка и расстояния**  
- Сначала проектировать desktop в **1440 px** и mobile в **375–390 px**, затем адаптировать промежуточные экраны.  
- Для контента ориентир `max-width: 1200–1320px`, с боковыми полями, зависящими от ширины экрана.  
- Единый spacing scale, а не случайные отступы в каждом компоненте.  
- Скругления небольшие и последовательные; исключение — плавающий хедер и отдельные CTA.  
- Не штамповать одинаковые «карточки с иконкой» для всех секций.

**7. Анимации и скролл-история**  
**Базовый приоритет: убедительная статическая верстка**  
Анимация — усиление существующей композиции, а не её замена. Для первого согласования **достаточно статического макета** с пояснениями по движению.  
**Уровень 1 — допустимая базовая реализация**  
- Короткие появления содержимого при входе в viewport, без агрессивного движения.  
- Мягкая смена цвета фоновых поверхностей между секциями **без резких вспышек**.  
- Небольшой сдвиг/масштаб изображения при прокрутке, если это не ухудшает плавность.  
- Hover/press состояния кнопок; плавная прокрутка к якорям с учётом reduced-motion.  
**Уровень 2 — эксперимент, после отдельного утверждения**  
- Sticky-секции каталога с синхронизированными текстом и объектом.  
- Управление поворотом **настоящей** 3D-модели от scroll progress.  
- Сложные последовательности переходов, WebGL/Three.js и тяжёлая кинематографичная анимация.  
**Условия для уровня 2:** есть подходящие 3D-модели (GLB/glTF), согласован отдельный объём работы, есть fallback для mobile и слабых устройств, подтверждены производительность и доступность. Без этого не подключать Three.js / React Three Fiber «на всякий случай».  
**Технические ограничения движения**  
- Предпочитать `transform`/`opacity`; не анимировать дорогостоящие layout-свойства на каждом кадре.  
- Не делать весь документ client component только из-за нескольких анимированных блоков.  
- `prefers-reduced-motion: reduce` должен убирать параллакс, сложный скролл-эффект и автоматические переходы.  
- В формах, меню и CTA взаимодействие должно быть возможно без анимаций.  
- Не подключать крупную библиотеку анимаций без осмысленного выигрыша. CSS/IntersectionObserver достаточно для простых эффектов; Motion или GSAP — если действительно требуется скролл-синхронизация и это согласовано.  
- Не использовать scroll-jacking, блокировку нативной прокрутки, автозапуск видео со звуком или чрезмерные задержки контента.

**8. Адаптивность**  
**Mobile (примерно 320–767 px)**  
- Одноколоночная структура, понятные интервалы и достаточно крупные элементы управления.  
- Хедер — компактный: логотип/название, кнопка меню и/или заметный контактный CTA; раскрывающееся меню с якорями.  
- Категории идут **в естественном вертикальном порядке**: заголовок → фото → описание → CTA либо фото → заголовок → описание — выбрать один читаемый паттерн.  
- Чередование «слева/справа» на mobile отменяется. Не заставлять читать текст зигзагом.  
- Не фиксировать сцену 3D во весь экран; если анимации сложные, заменять статичным фото.  
- Форма на всю ширину контейнера, кнопка отправки хорошо видна; файл можно выбрать стандартным контролом.  
- Высота секций должна определяться содержимым, а не жёсткими `100vh`, особенно при мобильной адресной строке.  
**Tablet / small desktop**  
- Переход с двух колонок в одну должен быть предсказуемым; изображения не обрезать так, чтобы терялась форма детали.  
- Проверять якорную навигацию, переноси́мые заголовки и нажатие CTA на промежуточных ширинах.

**9. Изображения и медиа**  
- **Настоящие фотографии продукции заказчик ещё собирает.** Не считать изображения из референсов или генеративные материалы подтверждёнными фактами о предприятии.  
- Для дизайна использовать нейтральные placeholders и пометки, где нужны реальные фото.  
- Допустимо улучшать пользовательские фото (фон, экспозиция, кадрирование), **не меняя геометрию изделия, размеры и конструкцию**.  
- Не заявлять «3D-модель конкретной продукции», если это лишь визуальная иллюстрация.  
- Для публикации оптимизировать размеры и форматы (WebP/AVIF, где уместно), применять responsive `sizes`, ленивую загрузку вне hero; важное изображение первого экрана — по стратегии LCP.  
- Реальные изображения категорий приходят из FastAPI + SeaweedFS, метаданные — из API. Предусмотреть fallback при пустой галерее.  
- Доверять `alt` из медиатеки при его наличии, для декоративных изображений использовать пустой `alt`, не дублировать заголовок бессмысленно.

**10. Связь дизайна с данными и техническим стеком**  
- Публичная часть: **Next.js + TypeScript**. Сохранять SSR/SSG и серверные компоненты там, где это выгодно; не переводить всё на клиент.  
- `GET /api/v1/categories`: опубликованные категории в порядке, с `id`, `slug`, `title`, `description`, массивом `images` (url/alt/размеры).  
- `GET /api/v1/contacts`: фактические контактные данные. При отсутствии координат не показывать фальшивую карту.  
- `POST /api/v1/requests`: `multipart/form-data`, один необязательный файл.  
- Публичный сайт **не обращается** к PostgreSQL и SeaweedFS напрямую с приватными ключами.  
- Управление каталогом через админку не должно требовать правок React-кода: количество и порядок категорий динамические.  
- Тексты остальных секций пока предполагались **статическими в Next.js**; не добавлять самовольно CMS, страницу-конструктор или API для всех текстовых блоков.  
- Не выводить в UI внутренние идентификаторы, статусы заявок или технические сведения о сервере.  
- Для данных предусмотреть состояния `loading`, `empty`, `error` с аккуратным отображением, без превращения страницы в набор скелетонов навсегда.

**11. Критерии качества («не AI slop»)**  
- Страница воспринимается как **цельный бренд-дизайн**, а не случайный набор UI-секций.  
- Есть 1–2 выразительных композиционных решения (hero и каталог), остальные блоки поддерживают их.  
- Нет шаблонных клише: гигантских свечений, бессмысленных glass-карточек, случайного набора 3D-иконок, фальшивых отзывов и надуманных KPI.  
- Ровная вертикальная ритмика, хорошая оптическая выравненность, согласованные радиусы и типографика.  
- Видно, что это **сайт производства полиуретановых деталей**, даже если скрыть название компании.  
- Продуктовые фото крупные и честные, реальные действия понятны без скролл-эффектов.  
- Текст читается, контраст достаточный, формы доступны с клавиатуры.  
- Быстрая первая загрузка; тяжёлая анимация не блокирует взаимодействие.  
- Хорошо работает на ширине 375 px и 1440 px, не только на одном скриншоте.

**12. Макеты и порядок согласования**  
**Этап A — визуальная концепция / прототип**  
1. Собрать **статичный desktop-макет 1440 px** всей страницы, проработав прежде всего header, hero и каталог.  
2. Показать **мобильный макет 375–390 px** и принципы перестройки чередующихся секций.  
3. Продемонстрировать 1–2 варианта hero/каталога **только если пользователь попросил выбор**; иначе предлагать один продуманный вариант.  
4. Отдельно и коротко описать планируемое движение при скролле. Не тратить время на реализацию 3D до утверждения.  
5. Согласовать цвета, типографику, порядок блоков и основные CTA.  
**Этап B — реализация**  
1. Семантическая адаптивная верстка и реальные якоря/CTA.  
2. Подключение категорий и контактов через API, работа формы.  
3. Базовые безопасные анимации (если одобрены).  
4. Оптимизация изображений и производительности.  
5. Проверка на desktop/mobile, доступности, загрузки файла и ошибок формы.  
**Чек-лист для визуальной приёмки**  
- За 5 секунд понятно, что производит компания.  
- Основные категории читаются и отличаются визуально.  
- В каждой категории можно перейти к отправке заявки.  
- Весь каталог на одной странице, без ненужных карточек товаров.  
- Есть отдельный акцент на изготовлении по чертежам.  
- Телефон и форма доступны быстро и с мобильного.  
- Нет вымышленных данных о предприятии.  
- Нет горизонтального скролла на mobile.  
- При отключении анимаций вся страница полностью функциональна.  
- Новая/скрытая/переставленная категория отображается корректно после изменения через админку.
